Architecture Pourquoi ce placement

On envoie au bureau la transcription,
pas le carton entier.

MS1 + MS2Mac

Travaillent sur les PDF et images lourdes : pas de transfert de fichiers vers Fedora.

MS3Fedora

Ne reçoit que du texte OCR léger : un vrai traitement distant.

PostgreSQLFedora

Insertion locale à MS3 ; résultats séparés des fichiers.

RabbitMQMac

Relie les étapes sans appels synchrones ; garde les messages en attente.

Le Mac est l'atelier qui prépare et lit ; Fedora est le bureau qui comprend et classe.
Enveloppe d'un message · contrat v1 (Pydantic strict)
{ "event_id": "9f2c…", // clé d'idempotence "event_type": "ocr.completed", // clé de routage "version": "v1", "document_id": "DOC-3F8A1C0B2D4E", "correlation_id": "RUN-…", "service": "ms2-ocr", "payload": { "pages": [{ "texte", "y_rel", "confiance" }], "moteur": "tesseract", "duree_ms": 1072 } }

Un champ inconnu ou une autre version : message refusé. Le texte OCR voyage car MS3 n'a pas accès au disque du Mac.

Fonctionnement La messagerie

RabbitMQ, le tapis roulant de l'atelier

Acquittement après succès. Un worker qui plante ne perd pas sa tâche.
Files durables, messages persistants et confirmations de publication.
prefetch = 1. Un document à la fois par worker : la charge se répartit.
3 tentatives (2 s puis 4 s), puis file d'erreur.
Erreur définitive (PDF corrompu) : processing.failed immédiat.

Du POST au JSON, étape par étape

Fonctionnement États et robustesse

Un statut clair, aucune tâche perdue

PENDINGdépôt accepté (API)
step.started
PROCESSINGune étape tourne
résultat écrit
COMPLETEDmême transaction que le résultat
FAILEDcause lisible, après tentatives

Un statut terminal n'est jamais rétrogradé, même si un message arrive en retard ou en double.

Panne d'un worker (T-07)

MS2 arrêté pendant un dépôt : le message attend dans docflow.ms2.ocr, puis le document passe COMPLETED au redémarrage.

Idempotence (T-08)

Le même event_id publié deux fois donne 1 résultat et 1 ligne de journal. Pas de doublon.

Traçabilité

MS3 consomme tous les événements : étapes, durées, attente en file et causes d'erreur pour chaque document.

Acquis

  • Trois microservices indépendants, reliés par RabbitMQ.
  • Réseau privé Mac ↔ Fedora stable, indépendant du Wi-Fi.
  • Aucune perte de tâche en cas de panne, aucun doublon.
  • Modèle entraîné qui bat la baseline sur un test jamais vu.
  • Débit ×2,9 en ajoutant des workers OCR.

Limites et suite

  • Mesures de performance en mode distribué réel (MS3 sur Fedora) à rejouer.
  • Énergie : protocole prêt (powermetrics), mesure à lancer en sudo.
  • Pas de photo de ticket papier : inclinaisons simulées seulement.
  • 21 tickets de test, dont 3 Intermarché : résultats indicatifs.
  • Une VM sur le même Mac : pas de tolérance à une panne physique.
