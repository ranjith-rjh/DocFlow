01 La chaîne de traitement

Un ticket, quatre files, trois microservices

Chaque service lit sa file, fait un seul travail, puis dépose le résultat dans la file suivante. Le fichier ne voyage jamais : seuls son chemin, puis le texte lu, passent dans les messages.

Pourquoi le texte voyage dans le message, et pas l'image ? MS3 tourne sur la VM Fedora et n'a pas accès au dossier storage/ du Mac. Le texte OCR pèse quelques Ko : on envoie au bureau la transcription, pas le carton. Les valeurs de l'exemple sont fictives.
02 Architecture applicative

Qui parle à qui, et par quel canal

Trois canaux seulement : HTTP entre le navigateur et l'API, AMQP (RabbitMQ) entre les étapes, SQL vers PostgreSQL. Les fichiers restent sur le disque du Mac.

HTTPAMQP (une couleur par étape)fichiers ou erreursSQL depuis l'API

Présentation

index.html servie par l'API, /docs de FastAPI, ou curl. La page se rafraîchit chaque seconde.

Logique applicative

API + MS1 + MS2 sur le Mac, MS3 sur Fedora, reliés par RabbitMQ. Elle s'étale donc sur les deux nœuds.

Données

Fichiers dans storage/ côté Mac, résultats dans PostgreSQL côté Fedora. Deux lieux, deux natures de données.

L'API lit directement la base sur Fedora (port 5432 ouvert au seul réseau 192.168.56.0/24 par pg_hba.conf). Elle écrit la ligne PENDING puis PROCESSING ; MS3 seul écrit le résultat ou l'échec.
03 Architecture de déploiement

Deux nœuds sur un seul Mac, un réseau privé fixe

Le Mac fait tourner Docker Desktop ; VirtualBox fait tourner une VM Fedora. Ils se parlent par le réseau « hôte uniquement » HostNetwork, qui ne dépend pas du Wi-Fi du lieu.

05 Chaque script, en détail

Ce qu'il fait, où il tourne, pourquoi

commun.py

Mac + Fedoraimporté par api, ms1, ms2, ms3

Tout ce qui touche à RabbitMQ, écrit une seule fois. Un service n'a plus qu'à fournir une fonction traiter(message).

FILESLes 4 files : pretraitement, ocr, extraction, erreurs. Échange par défaut de RabbitMQ : la clé de routage est le nom de la file.
ouvrir_canal()Connexion + déclaration des 4 files en durable=True : elles survivent à un redémarrage de RabbitMQ. Chaque service les déclare, donc l'ordre de démarrage n'importe pas.
publier(canal, file, msg)Message JSON en delivery_mode=2 : persistant sur disque.
lancer_service(nom, abonnements)Boucle principale : prefetch_count=1, mesure de durée, envoi vers la file suivante, gestion d'erreur, acquittement après traitement (schéma ci-dessous).
attendre_rabbitmq()Au démarrage, réessaie 30 fois toutes les 2 s : quand tout démarre ensemble, RabbitMQ peut mettre quelques secondes à répondre.
  • Acquittement après traitement : si un service meurt en plein travail, RabbitMQ redonne le message à un autre worker (ou au même, relancé).
  • prefetch = 1 : avec 3 MS2, chacun prend un ticket à la fois ; la charge se répartit toute seule.
  • Pas d'erreur sur une erreur : un échec dans la file erreurs n'est pas republié, pour éviter une boucle infinie.
  • RabbitMQ disparaît : le programme s'arrête, Docker (restart: unless-stopped) ou systemd (Restart=always) le relance.

api.py

Mac · conteneur apiuvicorn :8000

Entrée

Un fichier envoyé en multipart/form-data (champ fichier).

Sortie

Fichier dans storage/originaux/, ligne en base, message dans pretraitement, réponse 202.

Pourquoi sur le Mac

Point d'entrée de l'utilisateur ; doit écrire le fichier là où MS1 le lira.
POST /documentsRefuse vide (400), > 10 Mo (413), format inconnu (415). Crée DOC- + 8 hexadécimaux, range le fichier, INSERT (PENDING), publie, puis passe en PROCESSING. Base ou RabbitMQ absent : 503.
format_reel()Lit les premiers octets (%PDF, \x89PNG, \xff\xd8\xff) plutôt que l'extension : un .png renommé en .pdf ne trompe pas MS1.
GET /documents/{id}Ligne complète de la table, 404 si inconnue.
GET /documentsLes 20 derniers, pour le tableau de la page web.
GET /healthTeste la base et RabbitMQ séparément : "base": "injoignable" veut dire VM éteinte ou PostgreSQL arrêté.
GET /Sert index.html : pas de serveur web en plus.
  • Renommage en DOC-… : le nom d'origine contient la réponse (enseigne, date, total) et parfois des infos personnelles. La chaîne ne le voit jamais.
  • 202 Accepted : l'OCR prend environ une seconde ; l'API ne bloque pas, le client interroge ensuite le statut.

ms1_pretraitement.py

Mac · conteneur ms1pretraitement → ocr

Entrée

{document_id, fichier}

Sortie

pages : pretraite/DOC-…/page_1.png, une image par page.

Pourquoi sur le Mac

Il manipule les fichiers lourds de storage/ : aucun PDF ne traverse le réseau.
charger_pages()PDF → une image par page avec PyMuPDF, directement en gris, à 300 DPI (200 pour les tickets très longs, sinon la mémoire explose). Image → chargée et convertie en gris. Un PDF illisible lève « PDF illisible ou corrompu ».
agrandir()Image de moins de 1 000 px de large → ×4 en bicubique. Les captures Lidl font 412 px : Tesseract lit mal les petits caractères.
redresser()Essaie chaque angle de −10° à +10° sur une miniature 500 px et garde celui où la somme d'encre par ligne varie le plus.
ticket incliné → angle retenu
encre par ligne : alternance nette = texte droit

Droit, chaque ligne de texte donne un pic d'encre et chaque interligne un creux : la variance est maximale. Penché, l'encre se mélange entre les lignes et la courbe s'aplatit. Pas de niveaux de gris « artistiques » ni de binarisation : on évite tout traitement qui pourrait effacer un caractère.

ms2_ocr.py

Mac · conteneur ms2 (×N)ocr → extraction

Entrée

{…, pages}

Sortie

texte : toutes les pages lues, jointes par un saut de ligne.

Pourquoi sur le Mac

Il lit les pages préparées par MS1 dans le même storage/.
lire_texte()pytesseract.image_to_string(lang="fra", config="--psm 4"). Le mode 4 suppose une seule colonne de texte de tailles variables : exactement un ticket.
  • C'est le goulot : l'OCR prend l'essentiel du temps. Le Dockerfile fixe OMP_THREAD_LIMIT=1 : un cœur par conteneur, et on parallélise en lançant plusieurs MS2 (--scale ms2=3) qui se partagent la file ocr.
  • MS2 ne comprend rien : il ne cherche pas le total. Séparer « lire » et « comprendre » permet de changer de moteur OCR sans toucher à l'extraction.

ms3_extraction.py

Fedora · systemd docflow-ms3extraction + erreurs → base

Entrée

{…, texte, durees} depuis extraction ; {document_id, erreur} depuis erreurs.

Sortie

UPDATE de la ligne : COMPLETED avec les champs, ou FAILED avec la cause.

Pourquoi sur Fedora

Traitement distant sur données légères, écriture locale dans PostgreSQL ; démontre conteneurs + VM.
normaliser()Majuscules sans accents : « Intermarché à payer » → « INTERMARCHE A PAYER ». Rend les règles insensibles aux accents de l'OCR.
enseigne_par_regles()L'enseigne dont le nom apparaît le plus, sinon UNKNOWN. Sert de comparaison et de secours si le modèle est absent.
preparer_texte()Texte normalisé, chiffres remplacés par 0 : le modèle ne doit pas apprendre un numéro de carte ou un montant.
trouver_date()Première date JJ/MM/AAAA (ou -, ., année sur 2 chiffres) qui existe vraiment et tombe entre 2015 et aujourd'hui.
trouver_total()Cherche les libellés par priorité, écarte les lignes pièges, prend le dernier montant de la ligne (ou celui de la ligne suivante).
extraire()Assemble les 3 champs, EUR seulement si un total existe, et note methode_enseigne (modele ou regles).
enregistrer() · marquer_echec()UPDATE … WHERE document_id : rejouer le même message réécrit la même ligne, jamais de doublon.

La règle du total, en action

CAFE MOULU4,49
SOUS-TOTAL3,02
PROMOTION-0,50
A PAYER3,02
TOTAL ELIGIBLE3,96
TOTAL TVA0,16

Exemple fictif, tiré du doctest de trouver_total.

Ordre de priorité des libellés

TOTAL A PAYER›NET A PAYER›MONTANT DU›A PAYER›TOTAL TTC›TOTAL

Lignes ignorées (pièges)

SOUS-TOTALSOUS TOTALELIGIBLETOTAL TVATOTAL HTPROMOTION

Le montant est lu en Decimal, jamais en float : 0,1 + 0,2 ne doit pas faire 0,30000000000000004 sur de l'argent. La base le stocke en NUMERIC(10,2).

Le modèle d'enseigne

Texte OCR« Intermarché… 23,40 »
preparer_texte« INTERMARCHE… 00,00 »
TF-IDFchar_wb, morceaux de 2 à 4 lettres
Régression logistique3 classes, max_iter=1000
EnseigneCARREFOUR · LIDL · INTERMARCHE
  • Pourquoi des morceaux de lettres et pas des mots ? L'OCR déforme les mots (« INTERMARCH3 », « LlDL ») ; les fragments de 2 à 4 lettres résistent à ces fautes et captent aussi la mise en page (mentions légales, slogans).
  • Pourquoi ce modèle ? 109 tickets d'entraînement : un modèle linéaire léger apprend vite (quelques secondes), s'explique facilement et tient dans un fichier .joblib chargé par MS3.
  • Ce qui est appris, ce qui ne l'est pas : seule l'enseigne est apprise. Date et total restent des règles : elles font déjà 100 % sur le test, un modèle n'apporterait rien de mesurable.

index.html

servie par l'API · tourne dans le navigateur

Un rectangle où l'on glisse les tickets (ou clic pour choisir), puis un tableau des 20 derniers documents rafraîchi chaque seconde par GET /documents. Statut coloré, cause d'échec au survol, durée de bout en bout calculée par updated_at − created_at. Pas de framework : HTML, CSS et quelques lignes de JavaScript, l'interface n'étant pas l'enjeu du projet.

entrainement.py

hors ligne · conteneur outils≈ 20 s
1. Annoterle nom du fichier donne la réponse
2. OCRcode de MS1 + MS2, en parallèle, cache data/textes/
3. Découper80 / 20, stratifié, random_state=42
4. Entraînersur les 80 %
5. Évaluerrègles contre modèle sur les 20 %
6. Sauvermodels/ + reports/evaluation.md
  • Annotation par le nom : <entite>_<AAAA>-<JJ>-<MM>_<montant>, saisi à la main (attention, jour avant mois). Exemple fictif : carrefour_2025-17-04_12.34.pdf.
  • Cache OCR : l'OCR de 137 tickets est le plus long ; relancer l'entraînement ne le refait pas. Supprimer data/textes/ si MS1 ou MS2 change.
  • Stratifié et figé : chaque enseigne est présente des deux côtés et le découpage est identique à chaque exécution, donc comparable.
  • Pourquoi dans Docker : l'image contient déjà Tesseract français et les mêmes versions de bibliothèques que les services.

mesures.py

hors ligne · conteneur outilsappli lancée

Dépose N tickets d'un coup (30 par défaut, répartis sur les enseignes) via http://api:8000, attend qu'ils soient tous COMPLETED ou FAILED, puis calcule la durée moyenne de bout en bout, la durée moyenne de MS1 et de MS2 (enregistrées par les services dans durees) et le débit en tickets par minute. Ajoute une ligne datée à reports/mesures.md. À lancer avec 1 puis 3 MS2 pour montrer le passage à l'échelle.

schema.sql

Fedora · PostgreSQLappliqué par installer.sh

Une seule table documents (détail en section 09). L'API crée la ligne, MS3 la complète. CREATE TABLE IF NOT EXISTS : on peut relancer l'installation sans rien casser. Un CHECK limite status aux quatre valeurs.

Dockerfile · docker-compose.yml

Mac
  • Une seule image python:3.12-slim + tesseract-ocr-fra + requirements.txt + tous les .py. Chaque conteneur lance juste une commande différente : un seul build, des services identiques.
  • Ancre YAML x-docflow : réglages communs (image, variables, volume storage, attente de RabbitMQ sain) écrits une fois.
  • depends_on: service_healthy : API, MS1 et MS2 démarrent quand rabbitmq-diagnostics ping répond.
  • DATABASE_URL pointe vers 192.168.56.10:5432 ; RABBITMQ_URL vers le service rabbitmq du réseau Docker.
  • Profil outils : ne démarre jamais avec up, seulement par docker compose run --rm outils ….
  • hostname: docflow-rabbitmq : RabbitMQ range ses données par nom d'hôte ; un nom fixe garde les messages entre deux démarrages.

fedora/installer.sh · fedora/docflow-ms3.service

exécuté dans la VM, en sudorelançable sans risque

1. PostgreSQL

dnf install postgresql-server python3, initdb si besoin, écoute sur toutes les interfaces, pg_hba.conf limité au réseau privé et à la VM.

2. Base

Utilisateur docflow avec le mot de passe de .env, base docflow, puis schema.sql.

3. MS3

Copie dans /opt/docflow, venv + requirements-ms3.txt, écrit ms3.env (600), installe et (re)démarre le service, affiche active.
  • Pourquoi systemd et pas Docker sur Fedora ? Montrer les deux techniques demandées par le cahier des charges : conteneurs côté Mac, virtualisation + service natif côté VM. systemd démarre MS3 avec la VM et le relance s'il s'arrête.
  • DynamicUser=yes : MS3 tourne sous un utilisateur temporaire sans privilèges, créé par systemd. After=postgresql.service : la base est prête avant lui.
  • Idempotent : chaque étape vérifie avant d'agir (grep -q, || true, IF NOT EXISTS), donc on le relance après chaque modification de MS3 ou du modèle.

verifier_reseau.sh

Mac · VM démarrée

Sans option : adresse 192.168.56.1 présente, ping vers la VM, port SSH 22, et ping depuis un conteneur Docker (le vrai chemin de MS1 et MS2). Avec --services : RabbitMQ sur 5672, PostgreSQL sur 5432 (depuis le Mac et depuis un conteneur), puis /health. Code de sortie 0 si tout passe. Le commentaire d'en-tête mentionne encore ./scripts/ (chemin V1) : le script est à la racine en V2.

.env.example · requirements.txt · requirements-ms3.txt

configuration
  • .env (copié depuis .env.example, jamais sur Git) : RABBITMQ_USER, RABBITMQ_PASSWORD, DB_PASSWORD. Lu par Compose côté Mac et par installer.sh côté Fedora : un seul endroit pour les secrets.
  • Versions figées (==) pour reproduire l'installation. requirements-ms3.txt ne contient que ce dont MS3 a besoin et la même version de scikit-learn que l'entraînement : sinon le .joblib risque de ne pas se recharger.

07 Technologies

Pourquoi celles-là, où elles tournent, ce qu'il faut

Python 3.12Mac (image) · Fedora (venv)
Rôle
Langage unique des 4 programmes et de l'entraînement.
Avantages
Toutes les briques IA et image existent ; un seul langage à relire ; code partagé (commun.py) entre Mac et Fedora.
Prérequis
Fourni par l'image python:3.12-slim ; python3 installé par dnf sur Fedora.
FastAPI 0.163 + uvicornMac · conteneur api
Rôle
API HTTP de dépôt et de consultation, page web.
Avantages
Très peu de code par route, réponses JSON automatiques, documentation interactive /docs offerte, upload via python-multipart.
Alternative
Flask : aussi simple mais sans /docs ni typage des paramètres.
RabbitMQ 3.13 + pikaMac · conteneur rabbitmq
Rôle
Faire passer les tâches d'une étape à l'autre, de façon asynchrone.
Plus-value
Découple les services ; files durables et messages persistants ; acquittement ; répartition entre plusieurs workers ; console web pour la démo.
Alternative
Kafka : pensé pour des flux énormes et rejouables, trop lourd ici. Appels HTTP directs : une panne de MS2 bloquerait toute la chaîne.
PostgreSQL + psycopg 3Fedora · paquet natif
Rôle
Garder statuts et résultats structurés.
Avantages
Types stricts (DATE, NUMERIC, JSONB), contraintes CHECK, accès réseau sécurisable par pg_hba.conf. psycopg passe les valeurs en paramètres : pas d'injection SQL.
Alternative
SQLite : un simple fichier, impossible à partager entre l'API (Mac) et MS3 (Fedora).
Docker Desktop + ComposeMac
Rôle
Lancer RabbitMQ, API, MS1, MS2 et les outils en une commande.
Plus-value
Tesseract et toutes les bibliothèques installés pareil partout ; redémarrage automatique ; --scale ms2=3 sans changer le code.
Prérequis
Docker Desktop lancé ; VM démarrée avant up.
VirtualBox 7.2 + Fedora 45 + systemdMac (hyperviseur) · VM
Rôle
Un second nœud, avec son propre système et sa propre IP.
Plus-value
Vrais échanges réseau entre deux systèmes ; réseau hôte uniquement indépendant du Wi-Fi ; Fedora ARM64 tourne nativement sur Apple Silicon.
Limite
Même machine physique : pas de tolérance à une panne du Mac.
T5
Tesseract + pytesseractMac · conteneur ms2
Rôle
Reconnaissance des caractères, modèle français.
Avantages
Libre, gratuit, hors ligne (aucun ticket envoyé à un service cloud), installé par un paquet Debian.
Réglage
--psm 4 pour une colonne ; un thread par conteneur.

11 Questions probables

Préparer les questions du jury

Est-ce vraiment distribué si tout tourne sur un seul Mac ?
Oui au sens logique : deux systèmes d'exploitation, deux adresses IP, des échanges TCP/IP réels (AMQP et SQL) sur un réseau privé. Non au sens physique : si le Mac s'éteint, tout s'arrête. On ne prétend pas à une tolérance aux pannes matérielles.
Pourquoi RabbitMQ plutôt que des appels HTTP entre services ?
Avec HTTP, l'API attendrait MS1, qui attendrait MS2… et une panne de MS2 ferait échouer le dépôt. Avec une file, chaque étape avance à son rythme, les messages attendent pendant une panne, et plusieurs MS2 se partagent la charge sans configuration.
Pourquoi seulement 4 files et pas un exchange topic comme en V1 ?
La chaîne est linéaire : chaque message n'a qu'un destinataire. L'échange par défaut (clé = nom de la file) suffit et se lit en une ligne. Le topic de la V1 servait au journal qui écoutait tous les événements ; en V2, les durées sont stockées directement avec le résultat.
Pourquoi MS3 sur Fedora, et pas MS2 ?
MS2 lit des images stockées sur le Mac : le déplacer imposerait de transférer chaque image. MS3 ne reçoit que du texte (quelques Ko) et écrit dans la base : il est le candidat naturel au traitement distant, et la base reste locale à son seul écrivain métier.
Qu'est-ce qui est vraiment de l'IA ?
Deux choses : l'OCR Tesseract (réseau de neurones LSTM pré-entraîné) et notre modèle d'enseigne entraîné sur nos tickets (TF-IDF + régression logistique). La date et le total sont des règles, et on le dit : elles atteignent déjà 100 % sur le test.
Comment évitez-vous que le modèle « triche » ?
Le nom de fichier (qui contient la réponse) est remplacé par DOC-… au dépôt ; les chiffres sont masqués avant le modèle ; les 28 tickets de test ne servent jamais à l'entraînement ; le découpage est figé (random_state=42).
Et si un message arrive deux fois ?
MS3 fait un UPDATE par document_id, clé primaire : la même ligne est réécrite avec les mêmes valeurs. Pas de doublon possible.
Que se passe-t-il pour une enseigne inconnue ?
Avec les règles : UNKNOWN. Avec le modèle V2 : il choisit toujours l'une des 3 enseignes connues, sans seuil de confiance. C'est une limite connue ; la V1 utilisait un seuil (0,55) et retombait sur les règles.
Pourquoi avoir simplifié la V1 ?
La V1 répondait à tout le cahier des charges mais faisait environ 5 000 lignes, difficile à expliquer en entier. La V2 garde les mêmes garanties essentielles (files persistantes, ack après traitement, idempotence, distribution Mac/Fedora, modèle entraîné) en environ 900 lignes. Elle abandonne les tentatives automatiques, le journal d'événements et les contrats Pydantic.
